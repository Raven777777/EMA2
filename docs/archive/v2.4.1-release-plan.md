# EMA2 v2.4.1 发布收尾建议

## 我建议按四步收尾

### 1. 冻结功能范围

明确 v2.4.0 就是当前功能基线。从现在开始，只接受四类修改：确认存在的错误、回归问题、文档不一致、影响安装或运行的发布问题。

其他新想法全部进入未来版本，不再改变当前架构。尤其不要因为 EMA2 没有内置 MCP、安全审查、网站适配器或其他脚本语言支持，就认为还欠缺什么。按照设计哲学，核心负责定义和执行浏览器原语，其他能力由外围扩展完成。

### 2. 完成最后一轮核验

测试体系已经相当具体：真实前台 Edge、Rust 自动化测试、明确的输出断言，以及真实浏览器验收。收尾时应该做一次完整复测，而不是继续扩大测试框架。

一个值得先修正的小问题：`CHANGELOG.md` 和 `HANDOFF.md` 写的是 `cargo test` 通过 71 项，但 `TESTING.md` 的自动化命令旁仍标注 68 项。发布前应统一这些数字，并以本次实际运行结果为准。

至少做一次接近用户实际使用场景的干净安装验证：从构建产物开始，加载 Edge 扩展，启动 daemon，执行几个关键操作，再验证断连、超时和停止服务的行为。确认发布包里的程序和文档与仓库当前版本一致。

### 3. 把安全边界写清楚，不必把安全功能塞进内核

EMA2 当前选择了本机回环通信，没有 token 或应用层授权。这个设计可以作为最小核心的明确取舍，但使用前提和风险必须清晰：它面向可信的本地个人环境，不应该随意暴露服务端口；能够访问该端口的本地程序可能获得浏览器操作能力。

收尾阶段只需要确保这个边界在 README 或安全说明里醒目、准确，不必为了追求“功能完整”而临时把认证、权限系统或复杂安全机制塞进内核。外围需要更严格防护的场景，可以独立实现或组合外部工具。

### 4. 发布，然后进入维护状态

当测试通过、文档一致、安装路径确认无误后，正式发布一个 GitHub Release，附上版本说明和可直接使用的发行包。README 负责让人快速理解项目、安装和开始使用；`CHANGELOG.md` 记录版本事实；`docs/TOOLS.md` 维护命令契约。不要让同一份信息在多处各自发展。

发布后进入维护状态，而不是停止维护：只修复真实缺陷，必要时做兼容性更新，不再主动扩大核心范围。只有当真实使用暴露出核心设计无法解决的问题，才重新考虑架构。

## 什么才算 EMA2 真正收尾？

一个不了解你开发过程的人，仅凭仓库、发行包和文档，就能理解 EMA2 的边界、独立安装它、正确调用它，并知道它在什么情况下不能保证成功。

达到这个标准，就可以发布。无需证明 EMA2 能完成所有网站上的所有任务，也无需把所有外围能力集成进来。
